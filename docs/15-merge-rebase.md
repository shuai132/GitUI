# 15. 合并与变基 (Merge / Rebase)

本模块提供完整的合并、变基及冲突解决工具链，支持标准的版本集成流与交互式历史修整。

## 核心职责

- **合并 (Merge)**：支持快进合并（Fast-forward）、普通合并（Non-FF）及压缩合并（Squash）。
- **变基 (Rebase)**：支持线性的非交互式变基，以及包含修补（Reword）、压缩（Squash/Fixup）、丢弃（Drop）和重排（Reorder）的交互式变基。
- **冲突解决**：提供集成的三路合并编辑器，支持按行选择冲突内容。
- **中间态管理**：实时感知仓库的中间状态（Merge/Rebase/Cherry-pick/Revert 中），并提供相应的操作横幅。

## 入口与交互流

### 触发机制
- **上下文菜单**：从历史视图的提交行触发合并、变基或消息修补（Reword）。
- **拖拽交互**：支持通过提交间的拖拽快速发起操作，并弹出动作选择对话框。
- **操作横幅 (Banner)**：当仓库处于中间态时，全局横幅提供“继续”、“跳过”或“中止”的便捷入口。中止操作使用应用内危险确认，并捕获仓库与操作类型；确认期间切换仓库或操作状态变化时，旧请求会被取消，避免作用到新的中间态。

### 合并方向
合并对话框的目标始终是当前检出的 HEAD 分支；源是要合入当前分支的引用。源候选包含本地分支和远程分支，因此远程分支尚未检出为本地分支时，也可以直接选择远程分支发起合并。

对话框保存打开时的仓库、HEAD OID / ref、目标分支和每个来源引用的 OID。打开后切换仓库或任一引用移动都会拒绝旧请求；后端在 Merge 写入前再次复核 HEAD 与所选 source OID。

历史图拖拽同样只作用于当前检出的 HEAD 分支，不表达“拖拽提交所在分支合入放置提交所在分支”的 branch-to-branch 操作。拖拽提交用于推导默认合并来源；放置提交用于当前分支的 rebase 目标。若要把某个分支合入另一个非当前分支，需要先显式切换到目标分支。

### 冲突解决工作流
1. **感知**：冲突文件以特殊状态出现在工作区列表中。
2. **编辑**：通过三路合并编辑器展示“当前分支（Ours）”、“目标分支（Theirs）”及“基础版本（Base）”。
3. **决策**：用户按行勾选需要保留的内容，系统实时合成输出预览。
4. **完结**：保存合成内容并标记为已解决，通过索引操作替换冲突条目。

冲突文件读取结果绑定 repoId 及当时 index 中 base / ours / theirs 三方条目的身份。编辑器慢响应只在仓库、路径和请求序号仍匹配时展示；保存合成内容、右键选择 ours / theirs 或标记已解决时，后端在写工作区前再次复核该身份。外部工具已解决或替换冲突时，旧操作被拒绝。二进制冲突不开放文本保存，只能显式选择某一侧。

## 数据集成逻辑

### 状态透传
后端在执行状态查询（Status）时，会同步采集仓库的中间态信息（如合并消息、变基进度等），并将其封装在 `RepoState` 中透传给前端 Store 及 UI 横幅。

### 变基计划 (Rebase Plan)
交互式变基在启动前会生成一个计划清单，允许用户在前端调整各提交的动作（Pick/Reword/Squash 等）及顺序。这些动作会在执行过程中由后端循环调度。

计划请求绑定打开时的 repoId、HEAD OID / ref、upstream 与可选 onto OID，延迟返回时再次检查请求序号和仓库上下文；旧仓库、旧引用或旧对话框的响应不会覆盖当前计划。启动时再次校验同一组精确目标，引用变化时不开始历史改写。

### 自动贮藏 (Autostash)
针对脏工作区场景，系统提供可选的自动贮藏与恢复机制，确保集成操作在干净的环境下进行，并在完成后尝试恢复用户的本地改动。

Pull、Merge 与 Rebase 共用同一套保守生命周期：创建 stash 后执行操作，再查询仓库状态；只有状态确认回到 clean 才 pop。若操作停在 Merge / Rebase 等中间态，或状态无法确认，原始改动继续保留在 Stash 列表，待用户解决或中止当前操作后显式恢复。

## 关键技术决策

1. **按行粒度合并**：合并编辑器优先保证行级冲突的选择效率，不支持在编辑器内直接进行文本编辑，以确保冲突解决的一致性。
2. **时间戳保留与修补**：在 Reword 或修补历史时，支持自定义作者与提交者时间，以满足精确的历史回溯需求。
3. **状态持久化**：变基计划等中间数据通过仓库内的临时文件进行持久化，确保在应用重启后仍能继续之前的操作流。
4. **错误兜底**：对于自动恢复（如 Autostash Pop）失败的场景，系统采取保守策略，保留 stash 并提示用户手动处理，避免造成二次代码丢失；集成操作本身的错误不会被恢复提示覆盖。
5. **提交拖拽事件**：历史提交行使用 pointer events 与命中测试实现拖拽，不依赖 HTML5 `draggable`。这让 Tauri 原生目录拖入可以跨平台取得绝对路径，同时保留提交源 / 目标高亮、动作选择和普通点击语义。

## 刷新与同步

任何集成操作的推进或终止都会自动触发全局状态（历史、分支、工作区）的刷新，确保用户始终看到最准确的版本拓扑。
