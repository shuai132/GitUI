# 增加开发版更新通道

## Context

正式自动更新只读取 GitHub Release 的更新清单，因此无法发现 `main` 分支最新成功构建。需要在不创建 Release 的前提下，为愿意尝鲜的用户提供一个独立的手动检查入口，并继续复用 Tauri updater 的签名校验、下载、安装和重启能力。

预期结果是：`main` 分支构建成功后，GitHub Actions 将最新的跨平台 updater 产物发布到独立分支；设置页可手动检查该开发版通道。启动时自动检查仍只关注正式版。

## 关键决策

- 正式版与开发版保持两个独立入口；启动时自动检查不触碰开发版，避免用户无意进入预发布通道。
- 不创建滚动 Release。开发版产物由 GitHub Actions 部署为只保留最新快照的 GitHub Pages 站点；这样既不累积发布记录，也不受普通 Git 分支单文件大小限制。仓库需将 Pages Source 设为 GitHub Actions。
- 现有三平台 Actions artifact 继续上传并保留七天，供手动下载测试；Pages 滚动快照只为应用内 updater 提供可匿名读取的原始更新包。
- 开发版使用“下一补丁版本 + Actions run number”的 SemVer 预发布号，使正式版可以升级到开发版、开发版之间可以按构建顺序升级，而同版本正式发布仍高于对应预发布版。
- `main` 构建通过 Tauri CLI 配置覆盖把该预发布号写入应用包，确保安装后的运行时版本与更新清单一致；MSI 内部使用等价的数字版本，满足 WiX 的版本格式约束。
- 下载与安装继续走 Tauri updater；更新包必须通过现有公钥验证，不自行实现安装或绕过签名。
- Pages 发布 Tauri v2 为当前安装格式生成的原生签名 updater 包；macOS 使用应用归档，Linux 与 Windows 使用对应的原生安装包，不依赖兼容旧版 updater 的额外压缩包。
- 清单中的产物 URL 包含版本和 commit 标识，避免静态托管缓存让新清单指向旧二进制。
- 开发版检查结果不参与正式版“跳过此版本”和“上次检查”状态，两个通道互不污染。

## 验证方式

1. 对版本与 updater 清单生成脚本运行单元测试，确认三平台映射、签名读取和缺失产物失败行为。
2. 运行前端类型检查与单元测试，确认两个按钮独立工作，开发版结果使用开发版对话框语义。
3. 运行 Rust 编译与单元测试，确认自定义 endpoint 检查命令可编译且已注册。
4. 将仓库 Pages Source 设为 GitHub Actions；在 `main` push 中确认三个构建 job 完成后部署滚动快照，再从正式安装包点击“检查开发版”，完成下载、签名校验、安装和重启。
