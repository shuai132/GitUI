# 变更文件排序偏好方案

## Context

有些仓库在几乎每次提交或工作区变更中都会出现固定的大文件，例如生成产物、锁文件或大型资源索引。用户通常不关注这类文件，但它们会占据变更文件列表的显眼位置，影响在提交详情和工作区中浏览真正需要关注的改动。

目标是在变更文件右键菜单中提供“移到最前”和“移到最后”，让用户按仓库独立记录文件路径的展示优先级。该机制只改变前端文件列表展示顺序，不改变 Git 数据、不改变提交内容、不影响 diff 读取和状态刷新。

## 关键决策

### 按仓库路径持久化

排序偏好使用仓库路径作为 key，而不是后端运行期 `repoId`。`repoId` 在应用启动后由后端重新注册生成，不适合作为长期偏好标识；仓库路径已经用于历史分支范围、默认远程等仓库级 UI 偏好。

建议存储结构：

```ts
type FileOrderBucket = {
  front: string[]
  back: string[]
}

type FileOrderPrefsByRepoPath = Record<string, FileOrderBucket>
```

`front` 记录固定在最前的路径，`back` 记录固定在最后的路径。一个路径只允许存在于一个 bucket；移动到最前时从 `back` 移除，移动到最后时从 `front` 移除。

### 展示层排序，不改 IPC

排序逻辑放在前端展示层：

1. 后端继续按现有逻辑返回 `WorkspaceStatus` 和 `CommitDetail.diffs`。
2. 前端拿到文件数组后，根据当前仓库路径应用排序偏好。
3. Diff 加载、暂存、取消暂存、文件历史等动作仍然使用原始路径和原始 diff index 映射。

这样不会改变 IPC 契约，也不会让状态刷新或提交详情加载变重。

### 排序规则

通用排序规则：

1. 当前列表中命中 `front` 的文件排在最前，顺序按 `front` 数组。
2. 未被记录的文件保持原始顺序。
3. 当前列表中命中 `back` 的文件排在最后，顺序按 `back` 数组。
4. 记录中不存在于当前列表的路径忽略，不主动删除，因为历史提交可能仍会用到。

右键单个文件“移到最前”时，把该路径插入 `front` 数组头部；“移到最后”时，把该路径追加到 `back` 数组尾部。多选时按当前视觉顺序作为一个块移动：移到最前时整块置于 `front` 头部，移到最后时整块置于 `back` 尾部。

### 路径口径

提交详情使用 `FileDiff` 的显示路径作为偏好 key：优先 `new_path`，没有则用 `old_path`。工作区使用 `FileEntry.path`。重命名文件会以新路径作为后续偏好；被删除文件用旧路径仍可命中历史提交中的记录。

### 列表视图与树形视图

列表视图完整应用“最前 / 最后”语义。

树形视图默认保留目录结构和字母序，不应用“最前 / 最后”偏好，也不展示排序菜单项。排序偏好只在列表视图中展示和生效，避免用户在树形视图中触发看不到结果的动作。

### 恢复默认位置

除了“移到最前”“移到最后”，建议提供“恢复默认位置”。它从 `front` 和 `back` 中移除当前文件或当前多选文件。没有这个动作时，用户只能通过反向移动改变 bucket，无法回到 Git 原始顺序。

### 容量与坏数据处理

偏好数据只保存路径字符串，规模很小。为避免长期使用后 localStorage 膨胀，每个仓库可设置软上限；超过上限时保留最近移动的记录。读取到非法 JSON、非法 bucket 或非字符串路径时回退为空偏好，并在下一次写入时覆盖为合法结构。

## 验证方式

- 单元测试：
  - `front` / `back` 命中时排序正确，未命中文件保持原始相对顺序。
  - 同一路径在 `front` 和 `back` 之间移动时不会重复。
  - 多选移动保持当前视觉顺序。
  - 不同仓库路径的偏好互不影响。
  - 非法 localStorage 数据不会导致组件崩溃。
- 手动验证：
  - 在提交详情变更文件列表右键某个常见大文件，移到最后后切换多个提交，文件持续出现在末尾。
  - 在另一个仓库打开相同路径文件，确认不会继承上一个仓库的排序。
  - 在 WIP 未暂存和已暂存列表分别移动文件，暂存 / 取消暂存 / diff 加载仍指向正确文件。
  - 列表视图中“移到最前 / 最后 / 恢复默认位置”立即生效；树形视图不显示排序动作并保持目录层级。
