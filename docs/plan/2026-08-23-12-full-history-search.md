# 全历史提交搜索

## Context

GitUI 已有历史搜索，但只过滤前端当前加载的提交；默认每页 200 条。目标提交在旧分页时，用户必须先反复滚到底，再搜索，SHA、作者邮箱和提交正文也没有完整匹配。

[GitHub Desktop 2026 功能反馈](https://github.com/desktop/desktop/issues/21543)明确提出在大仓库中按提交消息、作者和 SHA 搜索完整历史，避免手动滚动。GitUI 已有搜索入口和搜索态图隐藏，本阶段保留现有交互，只把结果来源改为后端完整 revwalk。

## 关键决策

- 搜索复用 `get_log` 的分支范围、远程分支、Stash 与丢失引用开关，不另造一套“看得到却搜不到”的范围语义。
- 查询在 Rust 内单次顺序扫描提交元数据，不读取 tree、diff 或文件内容；结果达到 201 条即停止，并只返回前 200 条。
- 前端输入至少 2 个字符后才发请求，300ms 防抖；等待期间先显示当前已加载分页的即时本地匹配，响应到达后切换到完整历史结果。
- 每次查询、仓库或过滤条件变化都递增请求序号，旧响应不能覆盖新结果。
- 搜索结果通常不连续，继续隐藏提交图；滚到底不触发 `loadMore`，避免把搜索变成全历史加载。
- 本阶段不做正则或模糊匹配，采用不区分大小写的包含 / SHA 前缀匹配，保持语义可预测。

## 验证方式

1. 在超过首屏分页的旧提交中按摘要、正文、作者姓名、邮箱和 SHA 前缀搜索，确认均可命中。
2. 切换分支范围、远程分支、Stash 与丢失引用开关，确认搜索范围与普通历史一致。
3. 制造超过 200 个匹配，确认只返回前 200 个并显示结果已截断。
4. 快速连续输入和切换仓库，确认旧响应不覆盖新查询。
5. 搜索时滚到底，确认不加载普通历史分页；清空搜索后恢复虚拟列表分页。
6. 在几千到几万提交仓库中输入稀有词，确认 UI 不阻塞且结果可接受。
7. 运行 `npx vue-tsc --noEmit`、`npm run test`、`cd src-tauri && cargo check`、`cd src-tauri && cargo test`。

验证结果：前端 225 个、后端 84 个测试通过，TypeScript 类型检查和 Rust 编译检查通过。在本机 3,131 个提交的仓库中用稀有无命中词扫描完整历史，未优化测试构建耗时约 67ms。
