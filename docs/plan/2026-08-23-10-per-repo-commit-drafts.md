# 按仓库保存提交信息草稿

## Context

GitUI 面向多仓库快速切换，但 `workspace` store 当前在活跃仓库变化时直接清空提交信息。用户写到一半去另一个仓库处理事情，再切回来时输入已经丢失；应用退出后也无法恢复。

[GitFourchette 2026 用户指南](https://gitfourchette.org/_static/GitFourchetteUsersGuide.pdf)把“保存提交消息草稿、稍后恢复”列为正式的高级提交工作流。GitUI 已有常驻提交输入框，因此本阶段采用更直接的自动保存：按仓库路径隔离草稿，输入后即时持久化，切换仓库或重启应用时自动恢复。

## 关键决策

- 使用仓库规范路径作为持久化键，不使用后端每次打开仓库都会重新生成的临时 UUID。
- 仅持久化非空草稿；成功消费后删除对应条目，避免存储无限堆积。
- 保存发生在本地 WebView 存储，不新增 IPC，也不把提交信息发送到网络。
- 切换仓库时先保存旧仓库输入，再载入新仓库草稿；不同仓库间绝不复用同一份文本。
- 提交和 Stash 等异步动作按“仓库路径 + 发起时原文”条件清理。等待期间若用户修改草稿或切到其他仓库，新内容不受影响。
- 本阶段不增加手动“保存草稿”按钮；常驻输入框本身就是草稿编辑器，自动保存减少额外操作。

## 验证方式

1. 在仓库 A 输入提交信息，切到 B 输入另一份，再往返切换，确认两份内容独立恢复。
2. 重建 Pinia store / 重启应用，确认当前仓库恢复上次未消费的草稿。
3. 普通提交、Amend 和用草稿作为 Stash 消息成功后，确认对应草稿移除；失败时保留。
4. 在提交等待期间切换仓库或继续修改输入，确认完成回调不会清掉新内容。
5. 运行 `npx vue-tsc --noEmit`、`npm run test`、`cd src-tauri && cargo check`、`cd src-tauri && cargo test`。

验证结果：前端 221 个、后端 82 个测试通过，TypeScript 类型检查和 Rust 编译检查通过。
