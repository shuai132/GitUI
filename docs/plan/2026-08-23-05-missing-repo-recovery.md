# 缺失仓库保留与恢复

## Context

GitUI 启动时会重新打开持久化名册中的每个仓库。当前只要 `open_repo` 失败，就把该路径从内存列表排除并立即回写成功列表；外接磁盘尚未挂载、网络目录暂时离线、权限短暂异常和目录移动都会造成仓库名册被静默永久删除，用户之后只能重新添加。

同类产品把“暂时打不开”和“用户主动移除”区分处理：

- [GitHub Desktop 缺失 worktree 反馈](https://github.com/desktop/desktop/issues/22473)展示其“Can't find this repository”状态会保留最后路径，并提供 Locate / Clone Again / Remove，而不是启动时直接删除。
- [GitHub Desktop 测试规范](https://fossies.org/windows/misc/desktop-release-3.4.20.zip/desktop-release-3.4.20/docs/process/testing.md)明确要求本地缺失仓库在重启后仍保留名称与最后路径，并允许用户显式移除。

本阶段让 GitUI 保留恢复失败项，在“所有仓库”中显示明确的不可用状态，提供原路径重试、选择新目录重新定位和显式移除。

## 关键决策

- 不把一次 `open_repo` 失败解释成用户移除；只有不可用行的显式移除动作才删除持久化路径。
- 不可用项只存在于前端名册，不注册到后端 `RepoManager`，不能成为 active repo，也不会启动 watcher / fetch。
- 原路径重试和重新定位都复用现有 `open_repo`；成功后才把不可用项替换为正常 `RepoMeta` 并激活。
- 普通的无效目录拖入仍只报告本次失败，不自动加入不可用名册；保留行为仅针对此前已持久化的仓库。
- 不新增 IPC 或磁盘扫描；Locate 使用现有目录选择器，用户明确指定替代位置。
- 正常仓库继续保持用户排序；不可用项追加在正常名册之后，恢复成功后进入正常列表末尾，避免给现有拖动排序模型引入隐藏占位索引。

## 验证方式

1. 在持久化名册中放入一个有效路径和一个不可用路径，启动后确认有效仓库正常打开，不可用项仍显示且配置未丢失。
2. 在不可用路径恢复后点击重试，确认行变为正常仓库并激活。
3. 把仓库移动到新目录后使用 Locate，确认旧路径被新路径替换且仓库正常打开。
4. 显式移除不可用项并重启，确认它不再出现。
5. 搜索可按不可用仓库名称或完整路径过滤；正常仓库切换、排序、拖入与快捷搜索不回归。
6. 运行 `npx vue-tsc --noEmit`、`npm run test`、`cd src-tauri && cargo check`、`cd src-tauri && cargo test`。
