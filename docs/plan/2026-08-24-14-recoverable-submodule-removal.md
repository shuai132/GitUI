# 可恢复地移除 Submodule

## Context

Git 官方把带本地修改的 Submodule 工作树移除视为需要显式 `--force` 的危险操作；当前 GitUI 的“删除 Submodule”实际执行更彻底的仓库移除，却直接递归删除工作目录和 `.git/modules` 元数据。即使列表已经识别出未提交修改，确认框也没有突出这一状态；确认打开后切换仓库，还可能让闭包按新的活动仓库执行同名目标。

预期结果：工作目录和内部 Git 元数据不再永久删除，而是移入系统废纸篓；确认框明确标出脏工作区与恢复方式，并把仓库 ID、Submodule 名称和路径绑定到确认快照。目标上下文变化时取消操作。

## 关键决策

- 保留现有“深度移除”功能范围，不把动作降级成仅 unregister；工作树、模块元数据、`.gitmodules`、本地 config 与 Index 仍一次处理。
- 用户数据目录只通过系统废纸篓移除，不直接递归删除；用户原本可通过 Git 恢复的父仓库配置 / Index 变更仍保留为可提交改动。
- 先处理工作树和模块元数据，任一步失败立即停止，不继续剥离 `.gitmodules`、config 或 Index。
- 确认快照不依赖确认时的“当前活动仓库”重新解析目标；上下文不一致时要求用户重新选择。

## 验证方式

1. 干净 Submodule 删除后，工作目录和 `.git/modules` 副本可在系统废纸篓找到，父仓库产生预期的待提交删除。
2. 带未提交修改的 Submodule 显示专门警告，确认后完整工作树进入废纸篓。
3. 模拟废纸篓失败，后端返回错误，尚未处理的目录和父仓库配置 / Index 保持不变。
4. 打开确认后切换仓库或刷新出不同目标，旧确认不会删除新上下文中的同名 Submodule。
5. 运行 `npx vue-tsc --noEmit`、`npm run test`、`cd src-tauri && cargo check`、`cd src-tauri && cargo test`。
