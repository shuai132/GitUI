# 可恢复的丢弃操作

## Context

GitUI 当前在文件级或全部丢弃时直接覆盖已跟踪文件并永久删除未跟踪文件，确认框也明确提示不可恢复。GitHub Desktop 与 VS Code 会把被丢弃的文件移入系统废纸篓，GitKraken 还提供丢弃 Undo；对误操作风险很高的入口，GitUI 应至少提供同等级的系统恢复通道。

预期结果：文件级、批量和全部丢弃先把当前工作区原件移入系统废纸篓，再从 Index 或 HEAD 恢复 Git 基线；废纸篓不可用时拒绝继续，绝不静默永久删除。批量丢弃合并为一次 IPC 和一次状态刷新，避免文件数增加时重复打开仓库与刷新界面。

参考：

- GitHub Desktop 官方文档：丢弃内容保存在废纸篓中的带日期文件内，清空废纸篓前可恢复。
- VS Code 官方 Source Control 文档：丢弃内容移入 Windows Recycle Bin 或 macOS/Linux Trash。
- GitKraken 官方文档：Discard 属于可 Undo 的工作区操作。

## 关键决策

- 直接把当前工作区原件送入系统废纸篓，再由 Git 从 Index 或 HEAD 恢复；不生成文本 patch，因此二进制文件、符号链接和未跟踪目录仍保留原始内容。
- 废纸篓操作失败即返回错误，不提供永久删除降级，避免用户以为内容可恢复但实际已丢失。
- 文件级丢弃恢复到 Index，全部丢弃恢复到 HEAD，保持现有 staged / unstaged 语义。
- 批量丢弃新增一个 IPC，一次处理全部路径并只刷新一次；保留单文件 IPC 供现有入口使用。
- 不把已跟踪的 gitlink 目标目录移入废纸篓，避免把完整 Submodule 工作目录误当作父仓库文件；父仓库只恢复 gitlink 状态。
- Hunk 级丢弃仍使用局部反向 patch，本次不承诺废纸篓恢复；若要支持，需要单独设计文件快照与局部恢复体验。

## 验证方式

1. 修改已跟踪文件后丢弃，确认工作区恢复到 Index，原修改版出现在系统废纸篓。
2. 新建未跟踪文件和目录后分别丢弃，确认原件进入系统废纸篓。
3. 同时选择多个已跟踪 / 未跟踪文件丢弃，确认只发起一次 IPC、只刷新一次，恢复结果正确。
4. 制造 staged、unstaged、untracked 混合状态并丢弃全部，确认工作区与 Index 回到 HEAD，ignored 文件保留。
5. 模拟废纸篓失败，确认 Git checkout 不执行，错误返回且没有永久删除兜底。
6. 运行 `npx vue-tsc --noEmit`、`npm run test`、`cd src-tauri && cargo check`、`cd src-tauri && cargo test`。
